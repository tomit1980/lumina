# Part A — fix the QA findings

## Context

The QA pass (committed `7c3c103`, findings in `docs/superpowers/qa/2026-09-07-qa-findings.md`)
produced 11 findings. This plan fixes **nine** of them and hands the remaining two to the
Supabase migration with a written plan rather than leaving them dangling.

The verification is unusually strong here: **six of the nine already have failing tests
waiting for them**, encoded by the QA suites as `it.fails(...)` — a Vitest form that passes
while the code is broken and *starts failing the moment it is fixed*. Fixing those six means
flipping `it.fails` back to `it` and watching them go green. Three need new tests.

Two Criticals lead. One loses user data while reporting success; the other lets any project
creator seize a confidential project.

## The fixes

### 1. QA-003 — Critical — Enter in a spreadsheet cell discards the edit

`components/documents/spreadsheet-editor.tsx:163-167`. The Enter handler calls
`e.currentTarget.blur()` and relies on `onBlur` (`:162`) to run `commit()`. Empirically that
path never fires — the workbook is never written, `onDirty()` never runs, Save stays
disabled — while a genuine click to another cell commits correctly.

**Do not chase the mechanism; make Enter independent of blur.** Call `commit` directly:

```tsx
if (e.key === "Enter") {
  e.preventDefault();
  commit(r, c, e.currentTarget.value);
  e.currentTarget.blur();
}
```

The subsequent blur is harmless — `commit`'s existing early return (`if (raw === current)
return;`, `:65`) makes the second call a no-op now that the workbook holds the value. That
guard already exists; reuse it rather than adding a flag.

### 2. QA-003b — Critical — Ctrl+S reports "Saved" having written nothing

`components/documents/document-page.tsx` `save()` guards on `!file || !editorRef.current ||
readOnly || saving` but **not** on `dirty`, so the keyboard path saves unconditionally and
toasts success. Add `dirty` to that guard. Ctrl+S keeps working whenever there are real
changes; with none, it does nothing instead of lying. This is a genuinely separate defect
from (1) — even with Enter fixed, a save that serialises an unchanged workbook must not
claim success.

### 3. QA-004 + QA-005 — Critical / High — project access has no object-level check

One root cause, one fix. `setChannelAccess` (`lib/store.tsx:765-773`) looks the channel up
and calls `channelIsManageable(s, channel)`. `setProjectAccess` (`:903-909`) checks only
`guard("project.create")` and never consults the project — so anyone holding that permission
can rewrite any restricted project's member list, including granting themselves editor.
`updateProject` (`:841-852`) has the mirror-image gap: `projectIsViewerOnly` is consulted
**only** inside `if (patch.attachments)`, so every other field skips the viewer gate.

Add a `projectIsManageable` helper beside `channelIsManageable` (`:207`), reusing the
existing `projectIsViewerOnly` (`:200`) and `actorRole`/`roleHas`:

```ts
function projectIsManageable(s: AppState, project: Project): boolean {
  if (roleHas(actorRole(s), "members.manage")) return true;
  if (project.createdBy === s.currentUserId) return true;
  return roleHas(actorRole(s), "project.create") && !projectIsViewerOnly(s, project);
}
```

Call it in **both** `setProjectAccess` and `updateProject` (for all patches, not just
attachments), denying with the same `deny(...)` copy style the channel path uses. Open
projects stay editable by project managers, which is existing intended behaviour;
restricted ones become creator / editor-member / admin only.

### 4. QA-007 — High — partially-corrupt state migrates "successfully", then crashes

`lib/store.tsx` `migrate()`: `activities: parsed.activities` and `lastRead: parsed.lastRead`
are the only two top-level fields without a `??` fallback. Add `?? []` and `?? {}`, matching
every sibling field. Without this, a blob missing either key is accepted as valid and the app
crashes on the first message sent or first unread count read.

### 5. QA-006 — Medium — a channel named "general" becomes undeletable

`migrate()`'s backfill `isTeam: c.isTeam ?? (c.name === "general" ? true : undefined)` is a
legacy heuristic, but `migrate()` runs on **every** load, so it re-applies forever. Gate the
heuristic on genuinely old data — only apply it when the persisted `version` predates the
`isTeam` field — rather than on every hydration. The hydration effect already has the parsed
version in hand; pass it into `migrate()` so the backfill can be conditional.

### 6. QA-008 — Medium — moving a task leaves gaps in the source column

`lib/store.tsx` `moveTask`: the renumbering map is built only from tasks matching the
*destination* status. Renumber the source column too when the status actually changed, so
`order` stays a dense `0..n-1` sequence on both sides.

### 7. QA-009 — Low — `createTask` returns `order: 0` always

The returned object is built before `update()` runs; the correct `order` is computed on a
separate copy inside the updater. Compute the column size once, before building the object,
and use it in both places so the return value matches what is persisted.

### 8. QA-010 — Medium — icon-only buttons have no accessible name

Seven visible buttons expose no name to assistive technology: the per-task quick-complete
circles in `app/page.tsx`, four icon buttons in `components/app-shell.tsx`, and the hover
toolbar in `components/chat/message-item.tsx`. Add `aria-label`s that say what the control
does, not what it looks like — "Mark *&lt;task title&gt;* complete", not "Circle". The codebase
already uses this pattern (`aria-label={`Share ${attachment.name} to chat`}` in
`components/attachments.tsx`); follow it.

### 9. QA-002 — Medium — a shared Markdown document can beacon on open

`components/documents/markdown-editor.tsx:30` sanitises correctly for scripting but leaves
remote `img` sources intact, so opening a teammate's document fetches attacker-controlled
URLs, leaking the reader's IP and the fact they opened it. Add a DOMPurify
`afterSanitizeAttributes` hook that drops `src` on `img` unless the protocol is `data:`, and
render a small "remote image blocked" affordance in its place so the author is not confused
by a silently missing image. Keep every existing sanitiser option — the XSS behaviour already
passes and must not regress.

## Deferred, with a plan — not dropped

Both are consequences of the same architecture: the entire workspace lives in one
`localStorage` blob. Plan 2 replaces that layer wholesale, so fixing them now is throwaway
work. Recording where each is genuinely closed:

**QA-001 (Critical) — every browser holds the whole workspace, private channels and other
people's DMs included.** Closed by the Supabase migration: the RLS policies already built and
probed in Plan 1 mean the server only ever sends a user rows they may see. It closes when
**Plan 2** swaps `lib/store.tsx` from localStorage to Supabase queries — at that point the
client physically cannot hold data it is not entitled to. Until then the current build must
not be given to a real team believing private channels are private; this is the single
strongest reason to finish Plan 2 before adoption.

**QA-011 (Medium) — ~83 ms of blocking main-thread work per state change at 13.4 MB.**
Caused by re-serialising every embedded file's base64 on every action. Closed by two Plan 2/3
changes already in the spec: the persist effect disappears when the store writes to Supabase
rather than to one blob, and file bytes move to Supabase Storage so they stop being part of
application state at all (spec Phase 2, "Storage"). No interim debounce: it is code Plan 2
deletes, and it would introduce its own risk of losing the final write.

Both should be re-verified after Plan 3 — QA-001 by confirming a guest's network responses
contain no restricted rows, QA-011 by re-running the 83 ms measurement.

## Ruling on QA-006 (made during execution)

The fix agent found that two existing tests in `tests/qa/invariants.test.ts` (around lines
159 and 178) claim to simulate "legacy data without `isTeam`" but persist the **current**
version number with the key deleted — byte-for-byte the same blob the new QA-006 test
persists while expecting the opposite outcome. No version threshold satisfies both.

**Ruling:** the old tests' *setup* is wrong, not their assertions. Two changes, both small:
1. Those two tests persist a genuinely old version (`1`), one line each, no assertion touched.
2. Root cause, in addition to the gate: `createChannel` writes `isTeam: false` explicitly,
   so a channel created today never has a missing key for the backfill to fall into. The
   gate (`version < SEED_VERSION`) then only matters for data that is actually old.

Cost if wrong: one channel named "general" created on a pre-fix build could still be
flagged on the next version bump. Accepted; it is exactly the legacy case the backfill exists for.
